# LeakSanitizer suppressions for `just sanitize` (plan.md Phase 6).
#
# Everything here is allocation MLT itself makes and never frees before
# process exit, not a leak in vimci's RAII wrapper. Each entry is scoped to
# a specific internal MLT frame, not to a blanket "ignore this crate" rule,
# so a real leak in `vimci_mlt::ffi` still fails the build.
#
# - mlt_factory_init: one-time module repository scan. vimci deliberately
#   never calls mlt_factory_close (see ffi::init doc comment) because closing
#   it while other services are still alive is worse than not closing it at
#   all; process exit is the only safe teardown point. Bounded, does not grow
#   with usage.
# - mlt_playlist_blank builds its blank entries through the same
#   factory+loader path a real producer takes, including the loader's
#   normalizing filters, and that state is never released. Matched on
#   `mlt_playlist_blank` itself (a public, exported symbol) rather than the
#   static `blank_producer`/`attach_normalizers` helpers it calls: those are
#   `static` functions the linker can identical-code-fold with unrelated
#   helpers, and matching on them silently suppressed a real leak in testing
#   (a `Producer` dropped via `mem::forget` still passed).
leak:mlt_factory_init
leak:mlt_playlist_blank

# Caveat: LeakSanitizer's stack scan is conservative (a stale pointer-shaped
# value left in a register or an unreused stack slot can spuriously "root"
# freed memory), so a clean `just sanitize` run is evidence, not proof, for
# any one refcount path. The primary guarantee is the `ffi` unit tests, which
# assert on MLT's own `ref_count()` directly rather than relying on ASan to
# notice drift.
